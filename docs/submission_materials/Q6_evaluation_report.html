5. Evaluation Methodology

Layer 1 — Automated Tool Routing

The evaluation/run_evaluation.py script sends questions to the live agent over the WXO REST API and counts real tool_calls events from the SSE response stream. A question passes if every expected tool fired and the agent returned a substantive answer.

Layer 2 — Human Response Quality Audit (2026-11-11)

All 20 initial agent responses were reviewed against actual SEC EDGAR data across eight quality dimensions: accuracy, completeness, clarity, units, temporal labels, source traceability, hedging, and scope behaviour. This audit identified five issues that the automated Layer 1 scorer could not detect.

Layer 3 — LLM-as-Judge (Arize Phoenix)

An Arize Phoenix harness with two modes: (a) Llama-agent runs using meta-llama/llama-3-3-70b-instruct as agent via the Code Engine MCP endpoint directly (superseded); and (b) production scoring where cached responses from the live WXO agent are scored by mistralai/mistral-small-3-1-24b-instruct-2503 with a 3-vote majority per question.

7. Interpretation

What the 100% routing score means

Tool routing (39/39) confirms the agent instruction set is working: for every benchmark question, the correct tool chain fired. This is a necessary but not sufficient condition for correctness — a question can pass routing while returning wrong values. The human audit and numeric anchors close this gap.

What the 100% scope score means

The agent never answered out-of-scope questions (stock prices, analyst forecasts, investment advice) from training data. It correctly declined three benchmark scope questions (BQ-21/22/23) and the fictional-ticker question (BQ-19).

What the 8/8 numeric anchors mean

Eight benchmark questions include specific dollar values as must-include checks (e.g. AAPL FY2026 revenue ~$478.8B, MSFT net income ~$133.7B). All eight pass within stated tolerances (0.5–2%), confirming the values are live EDGAR data, not training-data confabulation.

Key finding: All seven issues found by the human audit and Phoenix runs required server-side or instruction-set fixes — not just rephrasing the benchmark questions. The evaluation correctly identified meaningful quality gaps in a system that was already passing the automated routing check.
  • Issues 1–2 were high-severity (wrong entity, YTD-as-quarterly) and required server-side data fixes
  • Issues 3–7 were medium-severity and required either server-side fixes or instruction updates
  • All seven are resolved in v1.8.0

8. Completed Improvements (v1.8.0)

  • YTD filtering: get_quarterly_facts filters to 80–100 day duration window
  • Q4 derivation: annual minus nine-month YTD for USD flow concepts; derived rows labelled
  • Annual fact labelling: fiscal_year derived from period-end date; one row per fiscal-year end
  • Revenue concept selection: REVENUE_CANDIDATES evaluated server-side; newest period wins
  • Entity ranking: server ranks by has_recent_10k=true
  • Concept synonym guidance: Rule 7 expanded; sec_edgar_resolve_synonym tool added (~198 entries)
  • Source filing mandate: Rule 6 requires value stated before filing details; URL construction prohibited
  • filing_index_url in every fact row (computed from accession number and CIK)
  • Global SEC rate limiter: asyncio.Semaphore(8) via _edgar_get()
  • 14th tool: sec_edgar_resolve_xbrl_concept (7,462 FASB US-GAAP 2026 concepts; in-process inverted index)
  • XBRL derived-metric handling: canonical overrides for ROE, D/E, P/E, asset turnover, BVPS + EBITDA derivation
  • International ADR synonyms: TSMC/TSM, SAP SE, ASML Holding, Sony Group, Toyota/TM
  • 359 regression assertions across 21 test functions — all passing
